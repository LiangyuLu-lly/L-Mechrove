# beta18 — 老机型电池充电上限（运行时能力探测 + 双 EC 传输）设计

> 状态：设计已定稿（decision-complete）。本文档是后续实现任务的唯一事实来源，实现者不应再做任何额外决策。
> 依据：HEAD 工作区干净（`git status --short` 为空）。所有代码结论均标注 `file:line`，来自本仓库 HEAD 的实际阅读。

## 0 设计原则：本应用是官方控制台的替代品

> 这个应用本身就是用来**替代官方控制台**的 —— 任何逻辑都不该以"官方控制台/GCU 服务是否安装、是否在线、是否已连接、是否报告了状态"作为前置条件或门控。

对本功能（电池充电上限）的直接后果：

- (a) 不做任何控制台/服务存在性检查：不探测安装路径、不查进程、不查服务状态、不读其配置。
- (b) 能力判定只来自我们自己的探测与写后回读验证（§4），与厂商软件装没装、跑没跑、报没报状态无关。
- (c) 如果我们的路径走不通（传输打不开、探测失败），就如实告诉用户"本机不支持"，绝不退回"让官方控制台去设"。

同一原则横切整个应用：水冷连接策略 `LiquidCoolingConnectionPolicy.ShouldUseAutomaticDirectFallback`（`src\MechrevoLiteWin\Hardware\LiquidCoolingConnectionPolicy.cs:31-34`）目前把直连路径门控在"GCU 不可用"上，这是对该原则的已知违反，待修复；此处记录该横切原则，修复不在 beta18 范围内。

## 1 背景与现状（三条路径的实测结论）

本仓库里与"电池充电上限"相关的代码路径有三条，读代码 + 注释里的真机实测记录可以给出明确结论：**只有 EC 直写是真实路径**。

| 路径 | 结论 | 证据 |
|---|---|---|
| EC 直写（`\\.\ACPIDriver` + IOCTL） | **真实路径**。写 `0x7B9`（上限）/`0x7D0`（复充下限）后充电行为实测改变：设 80/60 时电量已在阈值之上 → 充电立即停止，5 分钟只漂 1%；设 96% 时停在 95% | `src\MechrevoLiteWin\Hardware\EcChargeLimit.cs:8-27`（真机实测 2026-09-11）、`:25-27`（本机复验） |
| ASUS ACPI 兼容层 | **空实现**。`DeviceSet` 直接 `=> 0`，什么都不做；注释明确"Mechrevo 不使用 ACPI 地址" | `src\MechrevoLiteWin\AsusACPI.cs:116-120`（两个 `DeviceSet` 重载都返回 0）、`:11`（"Mechrevo 不使用 ACPI 地址"）；`BatteryLimit = 0x00120057` 常量保留仅为兼容（`AsusACPI.cs:20`） |
| MQTT `BatteryProtection` 三档 | **只用于开机任务，且写的是模式位不是阈值**。它往 EC 模式位 DBAP(0x7A6) 写 0x08/0x18/0x28，不碰阈值寄存器，且模式位含义随机型而变 | `src\MechrevoLiteWin\Battery\BatteryControl.cs:88-90`（"官方那条路已按用户决定整体摘除"）；开机任务见 `src\MechrevoLiteWin\Program.cs:1619-1655` |

EC 直写路径的关键事实（全部来自 `EcChargeLimit.cs`）：

- 读 IOCTL `0x9C40A488`（入参 `[u32 地址]`，出参首字节即值），写 IOCTL `0x9C40A48C`（入参必须是 `[u32 地址][u8 值]` 共 5 字节；3/4 字节布局会被错位解析，DeviceIoControl 返回成功但寄存器纹丝不动；出参缓冲必须非空否则 ERROR_INVALID_PARAMETER(87)）——`EcChargeLimit.cs:10-14, 46-48`。
- 寄存器选型是一次返工：最初写固件字段表的 `CGLM @ 0x78F`，能写能回读却管不住充电；真正生效的是官方服务常量 `ADDR_BATTERY_CHARGE_LIMIT_UP = 0x7B9` 与 `ADDR_BATTERY_CHARGE_LIMIT_DOWN = 0x7D0`——`EcChargeLimit.cs:17-21`。
- 迟滞 5（`RechargeHysteresis`，`EcChargeLimit.cs:41`），范围 40–100（`EcChargeLimit.cs:43-44`）。
- `ValueFor`：100 ⇒ 写 0（固件"无上限"，出厂状态就是 0/0，实测能充满）；其余按百分比直写，实测 0x64/0x50/0x3C/0x28/0x14 全部原值读回不钳位——`EcChargeLimit.cs:70-78`。
- `TrySet`：先读旧值，写上限 → 回读确认；写下限失败则把上限还原（"只留半套阈值可能让 EC 行为不可预期"）；下限回读不符则把上下限都还原——`EcChargeLimit.cs:102-147`。
- `ReadPercent`：只读当前上限，失败返回 -1——`EcChargeLimit.cs:149-164`。
- **`IsSupportedMachine` 是硬白名单**：`model.Contains("YAOSHI")`，外加配置项 `ec_charge_limit`（"1"/"0"）可强制开关——`EcChargeLimit.cs:86-97`。

## 2 为什么老机型不生效（白名单 + 代码里的理由）

`IsSupportedMachine`（`EcChargeLimit.cs:91-97`）只放行型号字符串含 "YAOSHI" 的机器。老机型（非 YAOSHI 命名）即使硬件上走的是同一套 EC 寄存器，也会被拒：

- `SetBatteryChargeLimit` 在 `IsAvailableOnThisMachine()` 为假时直接拒绝并回显："EC 充电上限在本机型未验证，忽略 N% 请求"——`src\MechrevoLiteWin\Battery\BatteryControl.cs:106-112`。
- `ResolveDisplayLimitPercent` 同样跳过 EC 读，退回配置值，两者都不可信时返回 -1（未知）——`BatteryControl.cs:161-170`。

白名单存在的理由写在代码里（`EcChargeLimit.cs:87-89`）：**EC 字段布局随机型而变**。本机就是例子——固件字段表里的 `CGLM@0x78F` 能写能回读却管不住充电；在未验证的机器上按同一地址写等于往未知寄存器里塞值。这个担忧是真实的，但"型号字符串白名单"是错误的解法：它把"没实测过"和"不支持"混为一谈，且型号命名与 EC 布局没有可靠对应关系。

**决策 1（已定）**：用**运行时能力探测**替换型号白名单（见 §4）。`ec_charge_limit` 配置项保留为双向手动覆盖（"1" 强制支持、"0" 强制禁用），优先级高于探测结果——`EcChargeLimit.cs:93-95` 的现有语义不变。

## 3 目标与安全不变量

**目标**：让非 YAOSHI 命名的老机型也能用 EC 直写设置充电上限，同时不把"往未知寄存器写值"的风险放大。

**决策 4（已定，全部保留，逐条对应现有代码）**：

1. **每次写都回读确认**：`TrySet` 写后立即 `Read` 比对（`EcChargeLimit.cs:126-127, 135-140`）；`SetBatteryChargeLimit` 在写入失败时再读一次实际值，已是请求值才按成功收尾，否则如实回显（`BatteryControl.cs:124-139`）。
2. **下限写失败回滚上限**：只留半套阈值可能让 EC 行为不可预期（`EcChargeLimit.cs:129-140`）。
3. **绝不渲染伪造值**：unknown 就显示 unknown（`RestoreChargeLimitDisplay`，`BatteryControl.cs:172-185`；`AsusACPI.DeviceGet` 未映射返回 -1 的同一纪律，`AsusACPI.cs:89-114`）。
4. **用户手势凭证**：只有真实滑条手势（MouseUp/KeyUp）能捕获一次性凭证；UIA 拖拽、程序化写 Value 拿不到，拒绝并如实回显（`BatteryControl.cs:30-58`）。
5. **范围 40–100 与 100 ⇒ 0 语义不变**（`EcChargeLimit.cs:43-44, 74-78`）。
6. **EC 写放后台线程**，不卡 UI（`BatteryControl.cs:114-115` 的 `Task.Run`）。

## 4 运行时能力探测（决策 1）

**决策（已定）**：`IsSupportedMachine` 的型号白名单替换为如下探测流程。探测结果进程生命周期内缓存；`ec_charge_limit` 配置覆盖在两个方向上都优先于探测。

**步骤**：

1. 打开 `\\.\ACPIDriver`（或经 §5 的 DLL 兜底通道）。
2. 读 `0x7B9`，得到值 V。
3. **判据**：V 合格当且仅当 V == 0（固件"无上限"出厂态），或 40 ≤ V ≤ 100；**且**读 `0x7D0` 得到的下限值 ≤ 上限值（下限读失败时按"无法确认"处理，见失败呈现）。
4. **回写确认**：把 V 原值写回 `0x7B9`，回读必须等于 V。写回同一个字节即使该地址属于别的东西也是无害的（值没变）；只有这一来一回都成功，机器才被判定为"支持"。
5. 关闭句柄，缓存结论。

**判据的依据**：`ValueFor`/`PercentFor` 的语义（`EcChargeLimit.cs:74-82`）说明 0 与 40–100 是该寄存器仅有的两种合法状态；`0 ≤ 下限 < 上限 ≤ 100` 是社区工具强制的同一约束（`EcChargeLimit.cs:22-23`）。

**失败如何呈现**：

- 探测失败（读不到、回写不回声、下限 > 上限）→ 机器按"不支持"处理，UI 行为与今天的老机型一致：滑条请求被拒并如实回显（`BatteryControl.cs:106-112`），显示走 unknown 路径（`BatteryControl.cs:172-185`）。
- 探测失败**不弹窗、不阻塞启动**：探测在后台线程惰性触发（第一次需要做充电决策时），与 beta17 键盘探测的时机纪律一致（`docs\beta17-keyboard-fallback-design.md:47`）。
- 探测期间用户操作：探测未出结论前按"不支持"拒绝（保守方向），结论出来后缓存生效。

**探测无法检测到的东西（诚实边界）**：地址恰好是别的可写寄存器且回写恰好无害——回写同值在字节层面无副作用，但若该地址是带语义的命令寄存器（写任意值即触发动作），读-写-读也可能触发一次。缓解：判据要求 V 落在 0/40–100 且下限 ≤ 上限，随机寄存器同时满足的概率低；且探测只发生一次，不重复。残余风险见 §8。

## 5 双传输（决策 2）

**决策（已定）**：保留 `\\.\ACPIDriver` + IOCTL 为主传输；当设备无法打开（`CreateFile` 返回 INVALID_HANDLE_VALUE，`EcChargeLimit.cs:117-118`）时，回退到厂商 **`ACPIDriverDll.dll`** 的 `ReadEC(addr)` / `WriteEC(addr, value)` 导出（LoadLibrary + GetProcAddress）。

- **主传输**：现有 `Read`/`Write`（`EcChargeLimit.cs:166-198`）原样保留，签名不变。
- **兜底传输**：进程为 x64，DLL 为 x64，可直接 LoadLibrary。加载要求官方控制台的 DLL 已安装在机器上（本仓库不分发该 DLL）。
- **打开失败与 DLL 缺失的处理**：
  - IOCTL 打开失败 → 尝试加载 DLL；加载或GetProcAddress 失败 → 该次操作按"传输不可用"失败，走既有的如实回显路径（`BatteryControl.cs:124-139`），**不静默重试、不伪造成功**。
  - DLL 缺失是常态而非错误（老机型可能没装官方控制台），日志记一行即可，不刷屏。
- **回读验证语义在两条传输上完全一致**：`TrySet` 的回读确认与回滚逻辑（`EcChargeLimit.cs:126-140`）不感知传输来源。
- **串行化**：现有 `Gate` 锁（`EcChargeLimit.cs:50, 115`）继续覆盖两条传输，防止 IOCTL 与 DLL 通道并发碰 EC。

【待确认】`ACPIDriverDll.dll` 的确切导出名与签名（`ReadEC`/`WriteEC` 的参数与返回值类型）。本仓库无该 DLL 的任何引用或头文件；此信息来自姐妹项目（见 §7），实现前需在装有官方控制台的机器上用 dumpbin/依赖 walker 确认。

## 6 与官方控制台/开机任务的关系（决策 5）

**现状**：开机任务 `ApplyBatteryLimitAtBootAsync`（`Program.cs:1619-1655`，由 `charge` 命令触发，`Program.cs:248-255`）走 MQTT `BatteryProtection`：把配置的 `charge_limit` 折算成三档模式位（95+→0 性能/满充，80–94→1 平衡，<80→2 健康，`Program.cs:1624`），用 `MechrevoHw.HelperClientId` 连 broker——必须用辅助 client id，因为这个进程由计划任务在开机时拉起、会和常驻托盘进程重叠，共用 id 会互踢会话（`Program.cs:1625-1629` 注释）。发 `Report=GET` 轮询确认，10 次 × 300ms（`Program.cs:1636-1646`）。

**决策（已定）**：

1. **官方控制台/电源模式切换可能重设 EC 阈值**——这是开机任务存在的理由，也是交互路径写入后阈值可能被改回的原因。文档化结论：交互路径每次显示都从 EC 重读真实值（`ResolveDisplayLimitPercent`，`BatteryControl.cs:161-170`），被官方改回时界面如实反映，不假装我们的值还在。
2. **开机任务暂不携带新探测**。理由：开机任务走的是 MQTT 模式位路径，与 EC 阈值寄存器是两套东西（`BatteryControl.cs:88-90`）；给它加探测会把两条路径耦合，而探测需要 EC 传输可用（开机早期驱动/DLL 未必就绪）。**是否重设**的开放问题见 §9。
3. **决策 3（已定）：不做任何机型/控制台安装路径门控。** 姐妹项目用控制台安装路径区分新/旧控制台的做法**明确不移植**——不做安装路径探测、不引用装的是哪个官方控制台、连日志提示也不留。能力判定只来自 §4 的运行时探测与 `ec_charge_limit` 覆盖（§0 原则 (b)）。

## 7 与姐妹项目的差异与借鉴（含出处与授权说明）

**出处与授权**：以下机制描述来自姐妹项目 `github.com/CR1MSEN/MechrevoBatteryManager`（SHA `445ad456259c50fc8c69198c581b3e56943f2caa`）。**该仓库由本机主自己的团队编写，机主已明确授权从它复制**。本文档只描述机制，不粘贴其代码；实现时按本仓库的代码风格与安全接缝重写。

姐妹项目的机制（按机主提供的输入）：

- 用**安装的控制台路径**区分新/旧控制台——本项目**明确不移植**（决策 3，§0 原则）：不做安装路径探测、不引用装的是哪个官方控制台、连日志提示也不留。支持判定只依赖 EC 传输的运行时能力探测。
- 加载 `ACPIDriverDll.dll` 的 `ReadEC`/`WriteEC` 作为 EC 传输——本项目采纳为**兜底传输**（§5）。
- 同样的 `0x07B9`（读时掩码 `& 0x7F`）/ `0x07D0` 偏移，外加只读状态字节 `0x0742`。
- 在较新的（控制中心）控制台机器上**跳过下限写入**。
- "无上限"写 0；每次写都回读验证；下限写失败回滚上限；要求管理员权限。

与本项目现状的差异：

| 项 | 姐妹项目 | 本项目（beta18 后） |
|---|---|---|
| 机型判定 | 控制台安装路径（提示） | 运行时探测 + `ec_charge_limit` 覆盖；安装路径探测不移植（§0） |
| 传输 | DLL 为主 | IOCTL 为主，DLL 兜底 |
| 下限写入 | 新控制台机器跳过 | **仍写入**（现有 `TrySet` 语义，`EcChargeLimit.cs:129-140`）；是否跳过见 §9 开放问题 |
| 状态字节 0x0742 | 读取 | 本项目暂不使用；列为可选诊断增强（§9） |
| 读掩码 | `& 0x7F` | 本项目现有 `Read` 不掩码（`EcChargeLimit.cs:166-181`）；是否采纳见 §9 |

【待确认】姐妹项目上述机制细节（掩码、0x0742、跳过下限的条件、导出签名）均来自机主转述，未在本仓库内可验证；实现对应项前需对照该 SHA 的源码确认。

## 8 风险评估

至少以下五条具体失败模式，每条带缓解：

1. **写错寄存器**：探测判据通过但 `0x7B9` 在该机型上是别的语义寄存器，正常写入路径把垃圾值塞进去。缓解：探测的回写同值确认把"纯读探测"升级为"写路径可用性证明"；`ec_charge_limit=0` 一键禁用（`EcChargeLimit.cs:95`）；首次在真机写入前必须人工核对回读值（§10 步骤 6）。残余风险：写同值也可能触发带副作用的命令寄存器——无法从软件侧完全排除，只能靠真机验证收敛。
2. **DLL 位宽/版本不符**：`ACPIDriverDll.dll` 缺失、非 x64、或导出签名与预期不符 → LoadLibrary/GetProcAddress 失败或调用崩溃。缓解：加载失败按"传输不可用"如实失败（§5），主 IOCTL 路径不受影响；GetProcAddress 前先校验模块位数；调用包 try/catch，异常记日志不上抛 UI。
3. **EC 总线被拖住**：EC 操作慢或超时（`BatteryControl.cs:114` 注释明确"可能被 EC 总线拖住"），探测或写入卡住。缓解：所有 EC 操作已在后台线程（`BatteryControl.cs:115`）；探测加墙钟超时（建议 3s，超时按 Unknown/不支持处理，参照 beta17 探测的超时纪律 `docs\beta17-keyboard-fallback-design.md:48`）；`Gate` 锁防止并发操作叠加拖累。
4. **探测误判**：假阳性（地址是别的寄存器但值恰好落在判据内且回写成功）→ 后续正常写入污染未知寄存器；假阴性（瞬时打开失败）→ 支持的机器被拒。缓解：假阳性靠 §8.1 的真机验证 + 判据收紧；假阴性靠允许用户显式重探（`ec_charge_limit=1` 强制放行，或 UI 重试入口），且探测失败不写任何持久化的"不支持"标记。
5. **开机任务与交互路径互相覆盖**：官方控制台/电源模式切换重设 EC 阈值，或开机 MQTT 任务与用户刚设的 EC 阈值语义冲突（模式位 vs 阈值寄存器是两套状态）。缓解：显示永远以 EC 实际读数为准（`BatteryControl.cs:161-170`），被覆盖时如实回显；开机任务与交互路径写的是不同 EC 区域（模式位 vs 阈值），现有代码已分离（`Program.cs:1636` vs `EcChargeLimit.cs:126`）；§9 跟踪是否需要写入后的重读刷新。
6. **（附加）5 字节写布局错位**：IOCTL 写入参必须是 5 字节 `[u32][u8]`，错位会被驱动静默解析成错误地址（`EcChargeLimit.cs:11-14`）。缓解：现有 `Write` 已按 5 字节封包（`EcChargeLimit.cs:183-198`），双传输重构时此封包逻辑不得改动；测试接缝 `TrySetOverride`（`EcChargeLimit.cs:56`）继续保证单测不碰硬件。

## 9 开放问题（各带建议）

1. **是否在新控制台机器上跳过下限写入**（姐妹项目的做法）。建议：暂不跳过，保持现有"上下限成对写 + 失败回滚"语义；等真机验证发现新控制台固件对 `0x7D0` 写入有不良反应再收紧，并在文档补记。
2. **读 `0x7B9` 是否加 `& 0x7F` 掩码**。建议：探测判据本身已把合法值约束在 0/40–100，掩码与否不影响判据；若真机读到带高位标志位的值（如 0x80|V），采纳掩码并在 `PercentFor` 处理。列为真机验证时的观察项。
3. **状态字节 `0x0742` 是否引入**。建议：暂不引入；作为诊断日志的可选增强（读一次记日志），不参与任何判定。
4. **开机任务是否也走 EC 直写/携带探测**。建议：暂不改（§6 决策 2）；若真机证实官方控制台会在开机后重置 EC 阈值，再评估把 `charge` 命令扩展为"MQTT 模式位 + EC 阈值"双写，需先解决开机早期 EC 传输可用性。
5. **探测结论的持久化**。建议：进程内缓存即可，不写 config——探测每次开机重跑成本极低（两次读 + 一次同值写回），持久化反而引入"硬件变了配置没变"的陈旧风险。
